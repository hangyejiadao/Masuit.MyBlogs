# C# 开发规范

适用于本仓库中的 C# 项目。新增或修改代码时，优先遵循所在项目已有的命名、格式和架构约定；本文件用于统一新代码的基本要求。

## 目标框架与语言

- 新代码应兼容目标项目声明的目标框架，不要未经确认升级目标框架或引入额外运行时要求。
- 优先使用项目当前 SDK 支持的清晰、类型安全的 C# 语法。
- 保留文件现有的换行、缩进和命名空间风格；新文件使用四个空格缩进。

## 命名与代码组织

- 类型、方法、属性、事件和公开常量使用 `PascalCase`；局部变量和参数使用 `camelCase`。
- 接口名称以 `I` 开头；异步方法以 `Async` 结尾，除非框架或已有公共 API 约定了其他名称。
- 一个类型只承担一项清晰职责。将可复用逻辑放入已有的服务、扩展方法或基础设施层，不在控制器中堆积业务逻辑。
- 优先使用构造函数依赖注入；依赖应声明为具体需要的服务接口或类型，避免服务定位器和全局可变状态。
- 只为非显而易见的逻辑添加注释；注释应解释原因或约束，而不是重复代码。

## 类型安全与输入校验

- 为公开 API 和边界数据使用明确的类型；避免无必要的 `object`、动态类型、宽泛转换和抑制编译器告警。
- 对可空值显式校验或处理；参数不符合契约时使用项目一致的异常、验证结果或 HTTP 错误响应。
- 验证来自请求、配置、文件和外部服务的数据；不要仅依赖前端校验。
- 构造 SQL 时使用参数化 API。表名等标识符不能作为普通 SQL 参数时，必须进行严格白名单校验或安全引用。

## 异步、取消与资源管理

- I/O 操作使用 `async`/`await`，避免用 `.Result`、`.Wait()` 阻塞线程。
- 长时间运行或可中断的请求处理应传递并遵守 `CancellationToken`。
- 对 `IDisposable` 和 `IAsyncDisposable` 资源使用 `using` 或 `await using`，确保异常和取消时也释放资源。
- 不要吞掉异常。只捕获能够合理处理的特定异常；取消请求时仅在需要清理或正常结束时处理 `OperationCanceledException`。
- `finally` 中进行必要的资源或状态清理；清理失败不得静默伪装成业务成功。

## ASP.NET Core 与 HTTP

- Controller/Endpoint 负责 HTTP 输入输出和状态码，业务规则放在应用服务中。
- 流式响应（例如 Server-Sent Events）开始写入后，不得再返回会重新设置响应状态码或响应体的 MVC `ActionResult`。
- 处理已开始的响应时先判断 `HttpResponse.HasStarted`；此时不能再更改状态码或启动另一份错误响应。
- 对客户端断开连接的流式请求使用请求取消令牌退出，并在 `finally` 中清理连接状态。
- 新增或修改中间件、过滤器时，检查其执行顺序以及异常处理和响应压缩、缓存等中间件的交互。

## EF Core 与数据库

- 实体、模型配置、迁移和快照必须保持一致；结构变更应生成并审查对应迁移。
- 主业务上下文 `DataContext` 与日志上下文 `LoggerDbContext` 分别管理迁移，使用各自的迁移目录和迁移历史表。
- 不要手动修改已应用的迁移；不要提交没有实际结构操作的空迁移，除非有明确的迁移目的和说明。
- 自动迁移必须考虑现有数据库、旧库基线、并发应用实例和部署回滚；生产环境变更应先备份并在测试库验证。
- 对外部数据库操作使用参数化查询；注意事务边界、索引、约束和大表变更成本。

## 错误处理与日志

- 失败应明确向调用方或运维人员呈现，不要返回成功形状的默认值掩盖故障。
- 使用项目已有日志设施并记录必要上下文；不要记录密码、令牌、连接串、个人敏感数据或完整凭据。
- 异常应在能够恢复、补充上下文或转为明确应用错误的边界处理，避免重复记录同一异常后再原样抛出。

## 变更验证

- 修改后运行覆盖变更的最小构建、测试或静态检查；有对应测试时优先运行相关测试。
- 对数据库迁移、序列化、状态码、异步取消和流式响应等行为变化增加相应验证。
- 提交前检查差异，确认无无关文件、生成物、凭据、临时调试代码和空白错误。
- 文档或配置的变更应同步更新直接相关的使用说明。
